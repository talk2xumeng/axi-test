# E100c 写性能与读卡死测试报告

测试时间：2026-10-31 ~ 11-02。测试主机：10.6.9.78。写和卡死分析的代码版本：`72ee3c9`。

> **11-02 更新：读卡死已解决。** 原因是读请求 aruser 的 `sect_mask` 填了 0，按规格填写后 1~4 拍读都能满速运行。结果见[读：卡死已解决](#读卡死已解决)，字段定义见 [E100c_OISA包头定义.md](E100c_OISA包头定义.md)。

## 结论

| 项目 | 结果 |
|---|---|
| 4 对口并发读写（4 拍，30 秒） | **397.5G 数据**（写 187.3G + 读 210.4G） |
| 单对口读写混跑（4 拍，反射端 8 核） | **128.0G 数据**（写 64.0G + 读 64.0G）；同一方向读写不能叠加，见[读写并发](#读写并发) |
| 单对口双向打写（ens106 ⇄ ens101） | **199.7G 数据**（每方向约 100G） |
| 4 对口双向打写（8 个方向，4 拍，30 秒） | **511.9G 数据**，`err=0`、`lost=0`；受主机核数限制，见[4 对口双向打写](#4-对口双向打写11-03) |
| 2 对口双向打写（4 个方向，4 拍，30 秒） | **397.8G 数据**（每方向约 100G） |
| 4 对口并发只读（4 拍，30 秒） | **386.8G 数据**；读每帧 2~4 个事务时 **406.8G**，见[读写组合扫描](#读写组合扫描) |
| 4 对口并发只写（4 拍，30 秒） | **391.0G 数据** |
| 3 对口长稳（读、写、混跑各 4 小时） | 全程 `err=0`、`lost=0`，没有卡死；混跑时两个 NUMA0 对口间歇性塌陷，见[长稳测试](#长稳测试11-02-1842--11-03-0643) |
| 3 对口并发读写（4 拍，10 分钟） | **293.1G 数据**，全程 `err=0`、`lost=0` |
| 单对口写，最大带宽 | **126.1G 数据**（4 流 × 256，p50 15.70 µs） |
| 单对口写，建议配置 | **约 113G 数据**（4 流 × 200，p50 约 13.5 µs） |
| 3 对口并发写 | **322.0G 数据**（每对 4 流 × 200），`err=0`、`lost=0` |
| 读 | 已解决：`sect_mask` 填 0 时累计几十个读后卡死，只能给 E100c 重新上下电 |

- 放宽发送端总在途有效：总在途从 508 提到 800，单对口带宽约提高 36%，并发合计提高 32%。
- 发送端总在途到 1024 时芯片没有卡死，E100c 内的 `ost_max` 封顶在 511。
- 单流放大窗口没有效果，带宽停在约 44G，要用多流。
- 第 4 对口已换卡：ens105 换成 ens114。

下文“写”和“读：卡死分析”两部分的命令是当时的环境变量写法，现在的脚本不再使用这些变量，新用法看 `./scripts/e100c.sh help`。

## 测试环境

### 接线

| die | chip0 | chip1 | chip2 | chip3 |
|---|---|---|---|---|
| die0（`-s 0x38`） | ens101 | ens110 | ens103 | ens111 |
| die1（`-s 0x39`） | ens108 | ens119 | ens106 | ens114 |

表中是每个 E100c ETH 口对端的主机网口。die1 chip3 对端的网口，旧版本写的是 ens105（当时掉线、未测），现在用的是 ens114。NUMA0 的 4 张网卡都接在 chip 0、2 上，NUMA1 的都接在 chip 1、3 上，所以“同一个 NUMA 的对口”和“同一组 chip 的对口”是同一批对口，分不开。

主机是 2 路 CPU，每路 64 个物理核，开超线程，共 256 个逻辑核：NUMA0 是 0~63、128~191，NUMA1 是 64~127、192~255，核 N 的超线程是 N+128。

### 测试对口

`./scripts/e100c.sh <id> ...` 的第一个参数选对口。请求的 port id 从 die1 发出时，port p 到达 die0 的 chip p xor 2；反方向反过来。

| id | 发送 → 反射 | E100c 路径 | port id / b-port | NUMA | 发送端核 | 反射端核 |
|---|---|---|---|---|---|---|
| `0` | ens108 → ens103 | die1 chip0 → die0 chip2 | 0 / 0 | 0 | 27~43 | 44~52 |
| `1` | ens119 → ens111 | die1 chip1 → die0 chip3 | 1 / 0 | 1 | 65~81 | 82~90 |
| `2` | ens106 → ens101 | die1 chip2 → die0 chip0 | 2 / 0 | 0 | 1~17 | 18~26 |
| `3` | ens114 → ens110 | die1 chip3 → die0 chip1 | 3 / 0 | 1 | 91~107 | 108~116 |
| `e100c_r` | ens101 → ens106 | id 2 的反方向 | 0 / 2 | 0 | 借用 id 0 的核 | 借用 id 0 的核 |
| `e100c_r1` | ens111 → ens119 | id 1 的反方向 | 3 / 1 | 1 | 借用 id 3 的核 | 借用 id 3 的核 |
| `r0`~`r3` | id 0~3 的反方向 | | N xor 2 / N | 同正方向 | 正方向 4 流时空出的核 | 同左 |

- 每个正方向按满配置预留 26 个物理核：发送端 `-f 8 -s` 用 17 个（主核 + 8 个发送核 + 8 个接收核），反射端 `-r 8` 用 9 个（主核 + 8 个）。
- 反射端的核号要小于 128（DPDK 的 `-l` 只接受 0~127）。发送端用 `--lcores` 映射，可以放到超线程上。
- 借用核的对口不能和被借的对口同时跑。`r0`~`r3` 和正方向一起跑时，两边都只能用 `-f 4`、`-r 4`，脚本不检查核重叠。
- 每个 NUMA 可用 63 个物理核（留出核 0 和 64）。4 对口单向用满配置刚好放下，4 对口双向只能每方向 4 流 + 4 核反射端，详见[4 对口双向打写](#4-对口双向打写11-03)。

旧的 `PAIR=e100c` 等名字仍可用：`e100c` = id 2，`e100c_b` = id 0，`e100c_d` = id 1，`e100c_c` = id 3。

## 读：卡死已解决

### 原因

读请求 aruser[27:20] 是 `sect_mask`，表示请求的目标 sector，要按读长度填写。64 字节总线上 `sect_mask = {N{2'b11}} << {araddr[7:6], 1'b0}`，N 是拍数。之前发送端把它填成 0。

| 拍数 | sect_mask（地址 0） |
|---:|---:|
| 1 | `0x03` |
| 2 | `0x0F` |
| 3 | `0x3F` |
| 4 | `0xFF` |

`sect_mask=0` 时为什么 1 拍能跑、多拍累计几十个才卡，规格里没有说明，要问厂商。

### 验证

窗口 4，每帧 1 个事务，每 100ms 发 1 帧，不会拼包。

| 对口 | 拍数 | aruser[29:0] | 发出 | 完成 | 结果 |
|---|---:|---|---:|---:|---|
| ens108 → ens103 | 2 | 0 | 49 | 45 | **卡死** |
| ens106 → ens101 | 4 | 0 | 19 | 15 | **卡死** |
| ens108 → ens103 | 4 | 0 | 19 | 15 | **卡死** |
| ens119 → ens111 | 1 | `0x00300000` | 80 | 80 | 不卡 |
| ens119 → ens111 | 2 | `0x00F00000` | 80 | 80 | 不卡 |
| ens119 → ens111 | 4 | `0x0FF00000` | 80 | 80 | 不卡 |

后三行的抓包是 `ok_1beat_*`、`ok_2beat_*`、`ok_4beat_*`，在测试主机 `~/axi_pcap/`。

以下改动也试过，都不能解决卡死：反射端的 length 改成数据字节数、packing_num 改成拍数、`rlast` 置 1、每拍一个 R 头、ruser 取自 aruser（高 13 位或 tsn 所在位）、ruser 填 port。

C700 抓包里还有其他非 0 的 aruser 位（`client_id=2`、`snoop=1`、`ro=1`）和非 0 地址。4 拍只填 `sect_mask`（`0x0FF00000`）时吞吐和填全部位（`0x1FF20040`）基本相同，分别是 111.5G 和 111.3G。

## 读写并发

测试时间 11-02，对口 ens119 → ens111，4 拍，读写每帧各 2 个事务，各 20 秒，`err=0`、`lost=0`。

### 结论

- 同一方向的读写不能叠加：读写混跑最多约 128G，单读约 115G、单写约 113G。
- 混跑时反射端核数是一个瓶颈：4 核 110G，8 核 128G。反射端 4 核时忙碌率只显示约 70%，这个指标会低估负载，不能只凭它判断。
- 两个方向互相打写能接近叠加：ens106 ⇄ ens101 合计约 200G。
- 发送端核数不是瓶颈：发送端 8 流、16 流的结果相同。
- 推测同一方向的请求在 E100c 内共用一个按事务计的处理上限，单向约 55~62M 事务/秒。未验证，需要厂商确认。

- `--op mix` 可用于 E100c，读写各用一套 ID，每流窗口上限为 1024 /（流数 / 2）。

- 脚本：`-r N` 选反射端核数（1/2/4/8/16，默认 4），`--iso` 打开隔离模式，`e100c_r` 为 ens101 → ens106。4 对口的核重新分配，8 流加 `-s`、反射端 8 核时互不重叠。

- 写请求到不了反射端：ens101 的 ETH 计数和反射端抓包都是 0。

- UHUBT3 的响应是 0、ETHI3 是 10，所以响应应该产生在 ETHI3 和 UHUBT3 之间。这是根据计数器推断的。
- 少量发包时只看发送端发现不了：芯片正常时发 100 个写，平均时延也有约 150~170 µs。要核对反射端收帧数或 ETH、DNOC 计数。
