# E100c 写性能与读卡死测试报告

测试时间：2026-10-31 ~ 11-01。代码版本：`72ee3c9`。测试主机：10.6.9.78。

## 结论

| 项目 | 结果 |
|---|---|
| 单对口写，最大带宽 | **126.1G 数据**（4 流 × 256，p50 15.70 µs） |
| 单对口写，建议配置 | **约 113G 数据**（4 流 × 200，p50 约 13.5 µs） |
| 3 对口并发写 | **322.0G 数据**（每对 4 流 × 200），`err=0`、`lost=0` |
| 读 | **不可用**：累计几十个读后读响应卡住，只能给 E100c 重新上下电 |

- 放宽发送端总在途有效：总在途从 508 提到 800，单对口带宽约提高 36%，并发合计提高 32%。
- 发送端总在途到 1024 时芯片没有卡死，E100c 内的 `ost_max` 封顶在 511。
- 单流放大窗口没有效果，带宽停在约 44G，要用多流。
- 第 4 对口（ens105 → ens110）未测：ens105np0 多次从 PCIe 掉线。

## 写：单流放大窗口

对口 `e100c`，每帧 2 个事务，每事务 4 拍。

```bash
export FLOWS=1 REFL_CORES=1
BRIEF=0 ./scripts/e100c.sh refl --time 8                 # 反射端
T=5 ./scripts/e100c.sh snd write 800 --pack 2 --beats 4  # 发送端，800 换成各档窗口
```

| 窗口 | 发送二层 G | 数据 G | Mtxn/s | p50 µs | p99 µs | err / lost | 发送端 busy% | ETHI3 / UHUBI1 `ost_max` |
|---|---|---|---|---|---|---|---|---|
| 127 | 23.8 | 21.8 | 10.64 | 11.35 | 14.05 | 0 / 0 | 70 | 未测 |
| 254 | 41.3 | 37.7 | 18.42 | 13.30 | 14.90 | 0 / 0 | 88 | 未测 |
| 508 | 48.4 | 44.3 | 21.62 | 23.00 | 24.65 | 0 / 0 | 91 | 508 / 508 |
| 600 | 48.2 | 44.1 | 21.54 | 27.05 | 29.20 | 0 / 0 | 96 | 511 / 511 |
| 700 | 48.3 | 44.2 | 21.56 | 31.55 | 33.60 | 0 / 0 | 98 | 511 / 511 |
| 800 | 48.3 | 44.2 | 21.56 | 36.25 | 38.25 | 0 / 0 | 97 | 511 / 511 |

从 508 到 800，带宽不变，时延随窗口线性增加，多出来的在途只是在排队。约 44G 的上限更像是发送核造成的，因为同样总在途 508，4 流能到 83G；这一点没有单独验证。

## 写：单对口，4 流

```bash
export FLOWS=4
PAIR=e100c T=12 ./scripts/e100c.sh refl --time 12                  # 反射端
PAIR=e100c T=8  ./scripts/e100c.sh snd write 200 --pack 2 --beats 4  # 发送端，200 是每流窗口
```

`PAIR` 换成 `e100c_b`、`e100c_d` 可测其他对口。

### 在途扫描（ens106 → ens101，每档 5 秒）

| 每流 × 流数 | 总在途 | 发送二层 G | 数据 G | Mtxn/s | p50 µs | p99 µs | err / lost | ETHI3 / UHUBI1 `ost_max` |
|---|---|---|---|---|---|---|---|---|
| 127 × 4 | 508 | 91.1 | 83.3 | 40.65 | 11.80 | 14.40 | 0 / 0 | 505 / 505 |
| 160 × 4 | 640 | 108.3 | 99.0 | 48.35 | 12.45 | 15.25 | 0 / 0 | 511 / 511 |
| 200 × 4 | 800 | 124.2 | 113.6 | 55.46 | 13.45 | 16.50 | 0 / 0 | 511 / 511 |
| 256 × 4 | 1024 | 133.5 | 122.0 | 59.59 | 16.20 | 19.80 | 0 / 0 | 511 / 511 |

### 3 对口分别单独跑（每档 8 秒）

| 对口 | 4 × 200：数据 G / p50 / p99 µs | 4 × 256：数据 G / p50 / p99 µs |
|---|---|---|
| ens106 → ens101 | 114.9 / 13.30 / 16.20 | 126.1 / 15.70 / 19.15 |
| ens108 → ens103 | 112.6 / 13.60 / 16.60 | 122.5 / 16.15 / 19.75 |
| ens119 → ens111 | 113.3 / 13.55 / 16.65 | 120.8 / 16.40 / 20.00 |

以上都是 `err=0`、`lost=0`。从 800 到 1024，带宽只多约 7~10%，p50 多约 2.5 µs，已经开始明显排队，所以建议用 4 × 200。

## 写：3 对口并发

```bash
export FLOWS=4
for p in e100c e100c_b e100c_d; do PAIR=$p T=14 ./scripts/e100c.sh refl --time 14 & done
sleep 3
for p in e100c e100c_b e100c_d; do PAIR=$p T=8 ./scripts/e100c.sh snd write 200 --pack 2 --beats 4 & done
wait
```

| 每对配置 | ens106 → ens101<br>数据 G / p50 µs | ens108 → ens103<br>数据 G / p50 µs | ens119 → ens111<br>数据 G / p50 µs | 合计数据 G | 合计发送二层 G |
|---|---|---|---|---|---|
| 4 × 127（总在途 508） | 79.7 / 12.35 | 79.6 / 12.40 | 84.0 / 11.75 | 243.3 | 266.1 |
| **4 × 200（总在途 800）** | **103.6 / 14.85** | **103.6 / 14.85** | **114.8 / 13.30** | **322.0** | **352.2** |
| 4 × 256（总在途 1024） | 102.4 / 19.65 | 103.3 / 19.45 | 123.6 / 16.05 | 329.3 | 360.2 |

三档都是 `err=0`、`lost=0`，所有网卡的 `rx_discards_phy` 和 `rx_out_of_buffer` 都是 0。

并发只拖慢 NUMA0 的两对：4 × 256 时 ens106 这对从 126.1G 降到 102.4G，ens108 这对从 122.5G 降到 103.3G；NUMA1 那对没有下降。推测是主机 NUMA0 上的内存或 PCIe 竞争，未验证。

ens119 → ens111 这对的最大时延约 1 ms（其他两对约 300 µs），原因未查。

## 读：卡死分析

### 现象

读单独发能通，累计几十个后卡死：窗口 4 时，每帧 1 个读和每帧 2 个读都是发出 60 个、收回 56 个后停住（更早的估算约 48 个，当时的测试条件不同）。卡死后只能给 E100c 重新上下电。

**读响应卡在 die0 的 ETHT1 → UHUBI1 这一段。** 请求方向没有丢，反射端也都回了响应。目前分不清响应是卡在芯片里还是已被丢弃。

### 命令

```bash
export FLOWS=1 REFL_CORES=1
BRIEF=0 ./scripts/e100c.sh refl --time 8                              # 反射端，默认 R_USER=0x80
T=3 ./scripts/e100c.sh snd read 4 --rpack 1 --beats 2 --count 100     # 发送端读
T=3 COUNT=100 ./scripts/e100c.sh ping                                 # 发送端写（对照）

# DNOC 计数：发包前 start，发完 end
cd /home/mx/leix/mx_debug_e100c
sudo ./e100c_debug.py perf --option4 start
sudo ./e100c_debug.py perf --option4 end

# ETH 计数（读后清零）
cd /home/mx/mxfw_tools_e100c
sudo ./mx_eth_cli -c 4 -s 0x39    # ens106：stats show port 0 eth rx|tx chip 2
sudo ./mx_eth_cli -c 4 -s 0x38    # ens101：stats show port 0 eth rx|tx chip 0
```

### DNOC 计数（请求 / 响应）

路径：ens106 → ETHI3 → UHUBT3 →（跨 die）→ UHUBI1 → ETHT1 → ens101 → 反射端。ETHI3、UHUBT3 在 die1，UHUBI1、ETHT1 在 die0。

| 阶段 | 发送端 | ETHI3 | UHUBT3 | UHUBI1 | ETHT1 | `ost_cnt` |
|---|---|---|---|---|---|---|
| 写 100（对照） | 100 / 95 帧（响应被合并） | 100 / 100 | 100 / 100 | 100 / 100 | 100 / 100 | 0 |
| 读 20 | 20 / 20 | 20 / 20 | 20 / 20 | 20 / 20 | 20 / 20 | 0 |
| 读 100，发到 40 停住 | 40 / 36 | 40 / 36 | 40 / 36 | 40 / **36** | 40 / **40** | **4** |
| 卡死后写 10 | 10 / **10** | 10 / **10** | 10 / **0** | 0 / 0 | 0 / 0 | 0 |
| 卡死后读 10，发到 4 停住 | 4 / 0 | 4 / 0 | 4 / 0 | 4 / **0** | 4 / **4** | 4 |

### 响应逐段计数（读 20 + 读 100，共 60 个读）

| 位置 | 个数 | 结论 |
|---|---|---|
| ens106 进芯片的请求（ETH） | 60 | 全部进入芯片 |
| ETHI3、UHUBT3、UHUBI1、ETHT1 的请求（DNOC） | 各 60 | 请求方向没有少 |
| ens101 进芯片的响应（ETH，59 帧，其中 1 帧 284B 装 2 个） | 60 | 反射端全部回了 |
| ETHT1 的响应（DNOC） | **60** | 响应到了 ETHT1 |
| UHUBI1 的响应（DNOC） | **56** | **从这里开始少 4 个** |
| UHUBT3、ETHI3 的响应（DNOC） | 56 | 后面没有再少 |
| ens106 出芯片的响应（ETH） | 56 | 发送端收到 56 个 |

ETH 是这几个阶段的累计值，没有分阶段取到。反射端在读 20 阶段只收到 19 帧，按帧长推断是 E100c 把两个读并进了一帧，不是丢包。

### 每帧 2 个读，上电后不发写

上电初始化后没有发过写，也没有发过其他读：

```bash
T=3 BRIEF=0 ./scripts/e100c.sh snd read 4 --rpack 2 --beats 2 --count 100
```

| 位置 | 请求 | 响应 |
|---|---|---|
| 发送端 | 60（30 帧，计划 100 帧） | 56（56 帧） |
| ETHI3 | 60 | 56 |
| UHUBT3 | 60 | 56 |
| UHUBI1 | 60 | **56** |
| ETHT1 | 60 | **60** |
| 反射端 | 60（42 帧） | 60（42 帧） |

结果和每帧 1 个读（前面已发 100 个写）完全相同，卡在同一段，`ost_cnt` 都是 4。说明卡死与每帧事务数、之前是否发过写都无关。窗口 4 下无法区分上限是 56 个响应，还是最后 4 个在途总被卡住，需要换窗口验证。这一轮的 ETH 计数没有取到。

### 卡死后的写响应是假的

- 写请求到不了反射端：ens101 的 ETH 计数和反射端抓包都是 0。
- 发送端仍收到 10 个 `c803` 写响应，状态字节为 0。`axiperf` 显示 `txns=10 err=0`，数据其实没有送达。
- UHUBT3 的响应是 0、ETHI3 是 10，所以响应应该产生在 ETHI3 和 UHUBT3 之间。这是根据计数器推断的。
- 少量发包时只看发送端发现不了：芯片正常时发 100 个写，平均时延也有约 150~170 µs。要核对反射端收帧数或 ETH、DNOC 计数。

### 待厂商确认

1. ETHT1 收到读响应后，什么条件会让它不再发给 UHUBI1？是否和信用或 `ruser` 有关？
2. 卡死后，写响应为什么由 ETHI3 和 UHUBT3 之间产生，而且状态是成功？
3. 读响应卡住后，为什么写请求过不去，读请求却能走到 ens101？
4. DNOC 的 RSP 计数是否表示响应经过该节点？以上分析依赖这个假设。
5. 真实读响应的 `ruser` 应该填什么？测试用的是 `0x80`。

## 工具说明

- 总在途超过 512 时，发送端内部用 1024 个逻辑 ID，线上只发低 9 位，同一 ID 最多同时在途两次；响应按先发出的算。需要 `--ethertype`，且 `flows × window ≤ 1024`。
- 表中“发送二层 G”不含前导码和帧间隔，数据 G 只算 AXI 数据，事务固定 256B。
- 抓包解析脚本：[wireshark/oisa_axi.lua](../wireshark/oisa_axi.lua)。真实帧样例：[osia_10.txt](../osia_10.txt)。
